# Decision patterns from supplied examples

These are patterns to preserve when the author provides similar material. They are not facts to copy into another document.

## Benchmark review pattern

When the author supplies a Figma benchmark board or competitor analysis:

- record the original Figma link and the exact pages, sections, or frames reviewed;
- capture visible Notes, annotations, and comparison tables when the connected read-only Figma tools expose them;
- distinguish direct observations from the author's analysis;
- summarize the finding, not only the competitor feature list;
- connect each finding to a Design Option, requirement, decision, or Open Question;
- use a comparison table when multiple products or patterns are being evaluated;
- mark inaccessible content instead of assuming it is absent.

## Example 1: SL/TP

Use this pattern when the document includes research-led feature design across more than one product surface:

- separate current behavior and user/business problem;
- record competitor and indirect benchmark research;
- document interview segments and research questions;
- preserve product-specific differences such as desktop versus mobile or separate products;
- compare information-display and form options;
- connect MVP decisions to technical constraints;
- record validation, education, empty/error states, and future iterations;
- do not claim broad user impact without supporting data.

## Example 2: Order segregation and layout redesign

Use this pattern when one initiative contains several connected problem streams:

- keep the initiative context;
- separate order segregation, layout, and table/component streams;
- preserve quantitative analytics and definitions;
- compare information architecture options with Pros and Cons;
- connect UI decisions to API or backend constraints without turning technical constraints into user Evidence;
- document reusable components and scalability;
- distinguish Evidence, design rationale, and Success Metrics.

## Example 3: Market depth

Use this pattern when the evidence supports keeping the current behavior:

- check whether the reported issue is User, UX, Technical, or Business;
- separate problem severity, affected population, usage rate, and performance impact;
- verify metric denominators, time windows, and source links;
- document the risk of changing the current experience;
- allow the decision to be `No change` or `Defer`;
- state what would trigger a future review.
